# site 질환 페이지 스키마

`wiki/site/disease/<대분류>/<subtype>/` 아래 질환 페이지를 만들고 유지하는 규칙.
레퍼런스 구현은 **RA**(`wiki/site/disease/autoimmune/ra/`) — 새 질환은 이 폴더를 복사해서 시작한다.

> **이 문서의 위치**: 관장하는 대상(`site/`) 옆에 둔다. 스키마는 방법론이므로 공개돼도 무방하다 — `CLAUDE.md §0.1`의 "학생은 방법론과 빈 틀을 물려받는다"가 이 문서를 가리킨다.
> 폴더명 `_schema`는 페이지가 아님을 표시한다(Jekyll 기반 Pages라면 `_` 접두 폴더는 빌드에서 제외되어 저장소에만 남는다).
> **공개돼서는 안 되는 것은 스키마가 아니라 내용**이다 — §3 참조.

---

## 0. 대전제

1. **SSOT는 `wiki/syntheses/<disease>.md`** — site는 거기서 생성되는 산출물이다 (`CLAUDE.md §6.9`).
   site에만 있고 synthesis에 없는 새 사실을 만들지 않는다.
2. **`site/`는 공개된다** — `data.js`는 view-source로 전부 읽힌다.
   화면에 렌더하지 않는다고 안전한 것이 아니다. §3의 경계를 지킨다.
3. **숫자는 지어내지 않는다** (`CLAUDE.md §6.5`) — 확인 못 한 값은 `확인 필요`로 표시하고 확인처를 적는다.

## 1. 파일 구성

```
site/assets/css/disease.css        공통 스타일       — 질환 무관
site/assets/js/disease-page.js     공통 렌더 로직    — 질환 무관
site/disease/<대>/<질환>/index.html  껍데기 34줄
site/disease/<대>/<질환>/data.js     질환별 내용     ← 새 질환은 이것만 쓴다
wiki/site-meta/<질환>.md            유지보수 레이어  ← 비공개
```

`index.html`은 `data.js` → `disease-page.js` 순서로 로드한다.
`fetch`가 아니라 `<script src>`를 쓰는 이유: `file://`로 열어도 동작해야 하기 때문(CORS 회피).

`data.js`는 `window.DISEASE`에 아래를 넣는다.

```js
window.DISEASE = (function () {
  const meta = { id, title, domain, updated };
  const acts = [ { id, num, en, title, accent, blurb, sections[] } ];
  const sections = { <sid>: { number, title, act, questions[] } };
  const articleList = [ { id, section, title, aliases[], summary,
                          facts[], body[], related[], papers[], links[] } ];
  const glossaryTerms = {}; const glossaryPattern = /.../gi;
  return { meta, acts, sections, articles: articleList, glossaryTerms, glossaryPattern };
})();
```

## 2. 구조 — 4블록 × 2섹션 × 질문

### 블록 (`acts`)

| id | num | 제목 | 섹션 |
|---|---|---|---|
| A | 01 | 무엇인가 | 정의·분류 / 역학·질병부담 |
| B | 02 | 왜·어떻게 | 원인·위험인자 / 발병·진행 |
| C | 03 | 임상 | 진단·분류 / 치료·미충족 수요 |
| D | 04 | 연구 | 유전학·오믹스 / 최신 동향 |

색은 site 팔레트를 따른다 — A `#6f3a55` · B `#315d78` · C `#94553b` · D `#1f5d43`.

### 섹션 (`sections`)

- **번호는 블록마다 01부터** 다시 센다. 전역 통번호를 쓰지 않는다.
- 섹션 키는 의미 있는 slug: `def` `epi` `risk` `course` `dx` `tx` `omics` `now`.
- `lead`(소제목)는 필드로 두되 **렌더하지 않는다** — 바로 아래 질문 목록과 중복된다.

### 질문 (`sections[].questions`)

**질문 1개 = 문서 1개.** 이것이 불변 규칙이다.

```js
{ q: "어떻게 정의하고 분류하는가?", note: "만성 자가면역 → 활막 표적 → 전신질환", article: "ra-definition" }
```

- `q` — 화면에 굵게 나오는 질문
- `note` — 옆의 회색 개념 사슬. `→`로 흐름, `·`로 병렬
- `article` — 대응 문서 id. 없으면 `준비 중`으로 렌더된다

섹션당 질문 3~5개가 적정. 질문 세트는 질환마다 조정하되 블록의 성격은 유지한다.

**분량 기대치 — 8섹션 × 질문 3~5개 = 문서 30~35건.**
섹션당 문서가 1~2개로 나오면 질문을 잘못 쪼갠 것이다. 한 문서가 여러 질문에 답하고 있다는 뜻이므로 다시 나눈다.

## 3. 공개 / 비공개 경계 ← **가장 중요**

### `data.js`에 넣는 것 (공개)

`meta` · `acts` · `sections`(number·title·act·questions) · 문서의 `id` `section` `title` `aliases` `summary` `facts` `body` `related` `papers` `links` · glossary.

`aliases`는 화면에 안 보이지만 **검색 인덱스로 쓰이므로** 공개 파일에 둔다.

> **처음부터 갈라 쓴다.** `data.js`에 썼다가 나중에 옮기지 않는다.
> 사후 이관은 반드시 빠뜨리는 항목을 남긴다 — 실제로 이 규칙을 쓴 뒤에도 첫 복제에서 `gap` 34건이 공개 파일에 들어갔다.

### `wiki/site-meta/<질환>.md`로 빼는 것 (비공개)

| 항목 | 이유 |
|---|---|
| `conf` (§3 confidence 등급) | 내부 근거 판단 |
| `tier` · `updated` | 유지보수 스케줄 |
| `gap` (문서가 남기는 미해결 한 줄) | **연구 필요성의 재료** |
| 모순 플래그 (§5 contradiction) | 논쟁 지점 = 연구 진입점 |
| `updates[]` 변경 이력 | 유지보수 인덱스 |
| `wiki/concepts/...` 등 내부 경로 | wiki 구조 노출 |

### 섹션 자체를 만들지 않는 것

- **미해결 · 논쟁** — 무엇을 모르는가, 왜 못 풀었는가, 부족한 데이터
- **지금 해결 가능한 질문**
- **해결하면 어떻게 달라지는가 (기대효과)**

이 셋은 연구계획서의 필요성·기대효과 그 자체다. 공개 위키에 두지 않는다.
같은 내용은 `site-meta/<질환>.md` §1(gap 열)과 `syntheses/<disease>.md`에 남는다.

> 판단 기준 한 줄: **"교과서에 실릴 내용인가, 계획서에 쓸 내용인가."**
> 교과서면 site, 계획서면 site-meta.

## 4. 문체 — 구문형

서술형 종결어미(`~한다` `~된다` `~있다` `~이다` `~없다`)를 쓰지 않는다.
명사·명사형으로 끊고, `→`로 인과·순서를, `·`로 병렬을 압축한다. 소제목도 명사구로 쓴다.

| ✗ | ✓ |
|---|---|
| RA는 활막을 표적으로 하는 만성 자가면역질환으로, 치료하지 않으면 관절 파괴로 진행한다. | 활막(synovium)을 표적으로 하는 만성 전신 자가면역질환 — 무치료 시 관절의 비가역적 파괴로 진행 |
| 면역계가 자기 조직을 표적으로 삼는다는 점에서 퇴행성 질환과 다르다 | 면역계가 자기 조직을 표적 — 마모에 의한 퇴행성 관절질환과 근본적으로 다름 |
| 왜 조기진단이 어려운가 (소제목) | 조기진단의 장벽 |

용어는 `CLAUDE.md §6.7`을 따른다 — 유전자·변이·도구·통계 용어와 고유명사는 영어 그대로.

## 5. 수치 (`facts`)

```js
facts: [ ["라벨", "값", "출처", "연도", 확인필요:boolean] ]
```

### 5.1 먼저 찾는다 — `확인 필요`는 최후 수단

**본문을 쓰기 전에 웹 검색으로 수치를 채운다.** 처음부터 `확인 필요`로 두고 넘어가지 않는다.
`확인 필요`는 예외 표시이지 기본값이 아니다 — 이 순서를 지키지 않으면 페이지 전체가 빈칸으로 남는다.

최소한 다음은 검색해서 채운다.

- 전 세계 유병률·발생률·환자 수·질병부담 — GBD 또는 해당 질환 역학 메타분석
- 한국 수치 — HIRA·NHIS 청구자료, KOSIS, 국내 코호트 연구
- 진단 기준의 최신판과 발행 연도
- 치료 가이드라인 최신판(EULAR·ACR 등)과 개정 주기
- 주요 치료제의 반응률·안전성 연구 — 원 논문 서지사항(저자·저널·권호·DOI)까지

검색해도 안 나오는 것만 다섯째 칸을 `true`로 두고, 값 칸에 `"확인 필요 — <어디서 확인할지>"`를 적는다.
그리고 그 목록을 `site-meta`의 미확보 표(§7.4)에 옮긴다.

### 5.2 기록 규칙

- **값 · 출처 · 연도를 항상 함께** 적는다. 출처 없는 숫자는 넣지 않는다.
- 유병률(prevalence)과 발생률(incidence)을 섞어 쓰지 않는다.
- 한국 데이터는 **출처의 한계를 본문에 함께** 적는다.
  청구자료는 유병률이 아니라 **진료 인원**(청구 발생 기준)이며 미진단·미수진이 빠진다.
  국내 값은 연구·보도마다 산출 연도·방식이 달라 갈리므로, 어느 자료의 몇 년도 값인지 반드시 병기한다.

### 5.3 출처 간 값이 어긋날 때

**한쪽을 고르지 않는다. 둘 다 싣고 "혼용 금지"를 본문에 명시한다.**

> 실제 사례(RA) — GBD 연령표준화 유병률 0.21% vs 임상 문헌 통용치 0.5–1%. 2~5배 차이.
> 사례 정의와 모델링 방식이 다르므로 한 문장 안에서 섞으면 출처와 숫자가 어긋난다.

괴리 자체를 "수치를 읽을 때 주의할 점" 항목으로 본문에 남긴다 — 그게 다음 사람이 인용할 때 실수를 막는다.

`facts`는 역학 섹션 전용이 아니다 — 감별 비교표(01), 진단 기준 항목(05), 약제 계열(06)에도 같은 표를 쓴다.

## 6. 문서 (`articleList[]`)

| 필드 | 내용 |
|---|---|
| `id` | `<질환>-<slug>` (예: `ra-prevalence`) |
| `section` | 소속 섹션 키 |
| `title` | **질문 그대로**. 섹션의 `questions[].q`와 일치시킨다 |
| `aliases` | 검색용 — 한글·영문·약어·동의어 |
| `summary` | 한 문장 요약. 수치 + 함의 |
| `facts` | §5 |
| `body` | `[["소제목", ["불릿", …]], …]` — 소제목 2~3개, 각 3~4불릿 |
| `related` | 같은 질환 내 문서 id. 존재하는 id만 |
| `papers` | `[["Author Year, Journal", "https://doi.org/..."]]` — `papers.md` 표기를 따른다 |
| `links` | 공식 자료·통계 포털 등 외부 링크 |

`body`의 마지막 소제목은 **한계·주의**로 두면 좋다 — 그 내용이 `site-meta`의 `gap`으로 이어진다.

## 7. 유지보수

### 반감기 티어

| 티어 | 대상 섹션 | 갱신 주기 |
|---|---|---|
| `stable` | 정의·분류 / 원인 / 진행 | 60개월 |
| `slow` | 역학·질병부담 | 24개월 |
| `fast` | 진단 / 치료 / 오믹스 / 최신 동향 | 12개월 |

### `updates[]` — 변경 이력 (site-meta에 보관)

```
[연도, kind, 내용, 출처, affected[], check]
kind: guideline | drug | cohort | method
```

`kind` 4종이 **D-02 최신 동향의 문서 4개와 1:1**로 대응한다.

| kind | 갱신할 문서 |
|---|---|
| `guideline` | 진료 권고는 최근 어떻게 바뀌었는가? |
| `drug` | 새 치료제와 안전성 정보는 무엇인가? |
| `cohort` | 새 코호트·오믹스 데이터는 무엇이 생겼는가? |
| `method` | 새로 쓸 수 있게 된 분석 기법은 무엇인가? |

`affected[]`는 다른 블록에서 같이 고쳐야 할 섹션을 지목한다.
예: JAK 억제제 안전성 → `kind:"drug"` + `affected:["tx","dx"]`

### site export 절차

**트리거** — (A) 해당 질환 synthesis가 마지막 site 반영 이후 변경됨 (B) 6개월 정기(fast tier).

**site까지 올릴 기준** — ① 역학 수치 변경 ② 가이드라인·승인약 ③ 기존 합의 반전 ④ 새 코호트·분석기법.
이 넷이 아니면 synthesis에서 멈춘다. 논문 한 편으로 페이지를 고치지 않는다.

1. `syntheses/<disease>.md` 변경분(diff) 확인
2. `site-meta/<질환>.md` §3에 `updates` 한 줄 추가 — `kind` + `affected`
3. `kind` → D-02 대응 문서 갱신 (**항상**)
4. `affected` → 해당 블록 문서 본문 갱신 (걸렸을 때만)
5. `facts` 수치가 바뀌었으면 값·출처·연도까지 교체
6. `site-meta/<질환>.md` §1의 갱신일·`gap` 수정
7. `wiki/log.md`에 `## [YYYY-MM-DD] site | <질환>` 한 줄

### 7.4 `site-meta/<질환>.md` 구성 (고정)

레퍼런스: `wiki/site-meta/ra.md`. 아래 다섯 절을 반드시 포함한다.

| 절 | 내용 |
|---|---|
| §1 | 문서별 메타 표 — `문서 id \| 반감기 \| conf \| 갱신일 \| 남는 질문(gap)` |
| §2 | 모순 플래그 — synthesis의 `[!contradiction]` 이관 · **어느 문서 위치인지 명시** |
| §3 | `updates` 변경 이력 — `연도 \| kind \| 내용 \| 출처 \| affected \| check` |
| §4 | 갱신 순서 (위 절차 요약) + 트리거 |
| §5 | **수치 확보 이력 + 미확보 표** |

**§5가 가장 자주 빠지는데, 다음 사람이 이어받는 지점이 바로 여기다.**

- 확보한 값 — 출처를 서지사항·DOI·연도까지 적는다. 나중에 원문 대조가 가능해야 한다.
- 미확보 표 — `항목 | 확인처 | 쓰이는 문서`. 공개 페이지의 `확인 필요` 뱃지와 1:1로 대응시킨다.
- 검색으로 채울 수 없는 항목(직접 분석·조사가 필요한 것)은 따로 표시한다.
  예: 조직–혈액 대응 일치도, PRS의 국내 전이성, 국내 코호트 현황 — 이건 검색이 아니라 연구가 필요한 항목이다.
- 출처 간 값이 어긋난 항목이 있으면 그 내역과 현재 판단을 남긴다(§5.3).

## 8. 새 질환 만드는 절차

**순서를 지킨다. 특히 3(수치 검색)을 4(본문)보다 먼저 한다** — 뒤집으면 페이지가 `확인 필요`로 도배된다.

1. `wiki/syntheses/<disease>.md`가 있는지 확인 — 없으면 먼저 만든다(SSOT가 먼저다)
2. SSOT를 읽고 **질문 세트를 확정** — 8섹션 × 3~5개, 총 30~35문서 목표
3. **수치를 웹 검색으로 채운다** (§5.1) — 역학 · 진단 기준 최신판 · 가이드라인 개정 연도 · 치료 반응률·안전성 원 논문
4. `site/disease/autoimmune/ra/` 를 대상 경로로 복사 (`index.html` + `data.js`)
5. `index.html` — `<title>`·`description`·breadcrumb 수정. 상대경로 깊이(`../../../`) 확인
6. `data.js` — `meta` 교체, 질문 세트 반영, 문서 작성.
   **`glossaryTerms`·`glossaryPattern`을 해당 질환 용어로 교체**한다 — RA 용어(HLA·ACPA·FAP…)를 그대로 두지 않는다.
   비공개 필드는 처음부터 쓰지 않는다(§3).
7. `wiki/site-meta/<질환>.md` 생성 — §7.4의 다섯 절 전부
8. 상위 색인 갱신 — `site/disease/<대분류>/index.html`, 필요하면 `site/disease/index.html`
9. 검사 (§9) — 명령을 **실제로 실행**한다
10. `wiki/log.md`에 `## [날짜] site | <질환>` 한 줄

> **병행 작업 시**: 여러 에이전트가 동시에 질환을 맡을 때는 경로를 겹치지 않게 배정하고,
> 공유 파일(`assets/**` · `CLAUDE.md` · `_schema/**` · 상위 색인)은 아무도 건드리지 않는다.
> 상위 색인은 추가할 `<a>` 한 줄을 **보고만** 하고, 한 곳에서 몰아 반영한다.
> 스키마 변경은 파급이 크므로 한 곳에서만 결정한다.

## 9. 배포 전 검사

**명령을 실제로 실행하고 출력을 확인한다.** "통과했다"는 자기 보고로 갈음하지 않는다 —
이 스키마를 쓴 뒤에도 첫 복제에서 `gap` 34건이 공개 파일에 들어간 채 "완료"로 보고된 적이 있다.

```bash
D=wiki/site/disease/<대>/<질환>/data.js

# 1) 문서 수 · 질문 매핑 수 (같아야 함)
echo "문서: $(grep -c 'id: "' $D)   질문매핑: $(grep -c 'article: "' $D)"

# 2) 비공개 필드 유출 (0이어야 함)
grep -cE 'conf:|tier:|gap:|flags:|judgement:|wiki/(concepts|syntheses|ideas)' $D

# 3) 서술형 종결어미 (0이어야 함)
grep -cE '"[^"]{5,}(한다|된다|있다|이다|없다|않다)"' $D

# 4) 괄호 균형 (세 쌍이 각각 같아야 함)
awk '{o+=gsub(/{/,"{"); c+=gsub(/}/,"}"); ob+=gsub(/\[/,"["); cb+=gsub(/\]/,"]"); p+=gsub(/\(/,"("); q+=gsub(/\)/,")")}
     END{print "{",o,"}",c," [",ob,"]",cb," (",p,")",q}' $D

# 5) related·article 참조 무결성 (출력 없으면 정상)
ids=$(grep -oE 'id: "[a-z]+-[a-z-]+"' $D | grep -oE '[a-z]+-[a-z-]+' | sort -u)
grep -oE '(related: \[[^]]*\]|article: "[a-z]+-[a-z-]+")' $D | grep -oE '[a-z]+-[a-z-]+' | sort -u |
  while read r; do echo "$ids" | grep -qx "$r" || echo "BROKEN→$r"; done

# 6) glossary가 교체되었는지 (다른 질환 용어가 남아 있지 않은지 눈으로 확인)
grep -oE 'definition: "[^"]{0,40}' $D
```

- [ ] 질문 수 == 문서 수 · 목표 30~35건
- [ ] 비공개 필드 유출 **0건**
- [ ] 서술형 종결어미 **0건**
- [ ] 괄호 세 쌍 균형
- [ ] `related`·`article` 참조 전부 실재
- [ ] glossary가 해당 질환 용어로 교체됨
- [ ] `site-meta/<질환>.md`에 §1~§5 전부 존재 (특히 **§5 미확보 표**)
- [ ] `확인 필요` 뱃지와 site-meta 미확보 표가 1:1 대응
- [ ] 브라우저에서 실제 렌더 확인 (홈 → 블록 → 문서 → 검색)
- [ ] `wiki/log.md` 기록
